## 決定事項

### 1. 北の推定を早くする（`HeadingEstimator`）

- 推定を始めるのに要る標本を 20 → **8** にする（歩き始めて約 10 秒）
- 標本が 20 個に満たない間は、不確かさの下限を 8° ではなく **12°** にする（表示の条件は「15° 以下」のまま）。20 個以上で今までどおり 8°
- そのほかの条件（速度、進行方向の精度、外れ値の除き方、時間による増え方、追跡が途切れたら捨てる）は変えない
- `scripts/heading-analysis.py` も同じ値に合わせ、`--self-test` を直す

### 2. 曲がり角の矢印の高さと出し方（PLAN.md §2.5）

- 高さ: **目線の 0.6m 上**（`EYE_HEIGHT_METERS` を使い、地上約 2.2m）
- 描く範囲: 仰角 5° 以上の規則の代わりに、**仰角 0° より上**の部分なら描く（矢印だけの例外。目的地の光の柱は今までどおり 5° 以上）
- **曲がり角を過ぎるまで消さない。** 「過ぎた」は、次のステップに進んだとき（T18a の案内の計算で次の曲がり角が変わったとき）。15m 以内で消す今の処理をやめる
- 曲がり角から **10m 以内**では、見かけの幅を **8°** までに抑え（近づいても大きくなりすぎないよう縮める）、不透明度を **50%** にする
- 高速移動・追跡なし・北の推定なしか不確かさ 15° 超え・GPS の精度 20m より悪い・設定オフで消す、は今までどおり

### 3. 量子表現（UI.md §11）

- 曲がり角の矢印: 矢印の輪郭に沿って明るい点を並べ、点のまわりに薄い光のにじみを付ける。点は矢印の向きにゆっくり流れる（1 秒に 1m 程度）。面は塗らない
- 目的地の光の柱: 縦に並ぶ点がゆっくり上へ流れる柱と、上端に点でできたピン（T22 のボタンのピンと同じ形）
- 日中の見えやすさ: 点の芯は明るく（不透明度 100% まで。矢印の 10m 以内は 50%）、にじみは 30% 以下。点の見かけの大きさは視角 0.3° 以上（遠いほど大きく。今の線の太さの下限と同じ考え方）。矢印の大きさの下限（視角 5° 以上）はそのまま
- 点滅はしない。点の流れの更新は今の描き直しの頻度（最大 10 Hz、フェード中 30 Hz）の中で行い、毎フレームにしない
- 点の数は印ごとに 200 個以下（定数）。描画は今の `MeshEntity`（三角形で点とにじみを作る）でよい。別の方法を選ぶなら理由を最終報告に書く
- 色は `#7FDBFF`。信号の柱（T24）は変えない

### 4. 閉じるときのクラッシュ

アプリを閉じると、毎回次のクラッシュが起きていた（2026-11-24 の実機のログ）。

```
F/libc: Fatal signal 7 (SIGBUS), code 1 (BUS_ADRALN) ... (io.github.yamichi77.aurawalkinfo)
#00..#03 base.apk!libimpress_api_jni.so
...
androidx.xr.scenecore.spatial.rendering.impress.ImpressApiImpl.disposeAllResources
androidx.xr.scenecore.spatial.rendering.SpatialRenderingRuntime.destroy
androidx.xr.runtime.Session.destroyRuntimes
androidx.xr.runtime.Session.destroy
androidx.xr.runtime.Session.lifecycleObserver ...（Activity の終了）
```

- `Session.destroy` が描画の資源をまとめて解放するときに落ちている。アプリが自分で `close()` した `MeshBuffer`・`CustomMesh`・`KhronosUnlitMaterial`・`PanelEntity` などを、SceneCore がもう一度解放しようとしている（二重解放）疑いが強い。`spatial/` の `SpatialMarkMesh`、`SignalTotemPanel`、`SpatialMarks` の `close()`、`SpatialRenderDiagnosis` の片付けの順番と内容を、`gradle/libs.versions.toml` のバージョンの SceneCore のソース（資源の持ち主と解放の決まり）で確かめて直す
- 例: アクティビティの終了時は、アプリ側で資源を解放せず、エンティティを無効にするだけにして SceneCore に任せる。逆に、セッションが続く間に作り直す場合は、SceneCore の決まりどおりの順番で解放する
- 原因と直し方の根拠（ソースの箇所）を最終報告に書く。実機で閉じたときに落ちないことの確認はオーケストレーターが行う
