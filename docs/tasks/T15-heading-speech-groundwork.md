## 目的

T19b の「空の方位帯」には、頭が北からどちらを向いているかが要る。AURA には方位センサーの記載がないので、**歩いたときの GPS の進行方向**と、**グラスの追跡（ARCore の位置の移動の向き）**を突き合わせて、ARCore の座標系と北のずれを推定する。そのための推定のロジック、記録、分析スクリプトを作る。

あわせて、T18b の目的地の音声入力に向けて、AURA で音声認識が使えるかを調べる自己診断を作る。

**実機（adb）は使わない。** 実機での確認は、ユーザーが受け入れのときに行う。そのための手順とスクリプトを用意する。

## 1. 北の向きの推定（`HeadingEstimator`、純粋な Kotlin）

- 新しいパッケージ（例: `heading/`）に置く。Android に依存しない純粋なロジックにして、JVM の単体テストで確かめる
- 入力
  - GPS: 時刻、進行方位（度。北 0°、時計回り）、方位の精度（度。無ければ null）、速度（m/s）、位置の精度（m）
  - ARCore の頭の姿勢: 時刻、位置（ARCore の座標系の x, z、m）、頭の yaw（ARCore の座標系、度）、追跡の状態
- 考え方
  - 歩いているあいだの「ARCore の座標系での移動の向き」（位置の差から求める。頭の向きではない。歩きながら横を見ても影響を受けないため）と、「GPS の進行方位」の差が、ARCore の座標系と北のずれ（オフセット）になる
  - 窓（例: 5 秒）ごとに1つのオフセットの標本を作る。標本にする条件の初期値: 速度 ≥ 0.8 m/s、GPS の方位の精度 ≤ 20°（精度が無いときは窓の中の方位のばらつきで代用）、窓の中の ARCore の移動が 3m 以上、まっすぐ歩いている（窓の中の GPS の方位の円周標準偏差 ≤ 10°、ARCore の軌跡の直線度 = 始点と終点の距離 ÷ 道のり ≥ 0.9）、追跡が TRACKING
  - 標本は円周平均でまとめ、中央値から 20° 以上離れた標本は捨てる。最近の標本（例: 直近 20 個）を使う
  - 推定の誤差（不確かさ、度）を出す。標本のばらつきと数から計算し、最後の標本からの経過時間に応じて増やす（初期値: 1 分あたり 1°）。下限は 5°
  - 追跡が途切れたら、ARCore の座標系が変わるおそれがあるので、推定を捨てて最初からやり直す
- 出力: オフセット（度）と不確かさ（度）、または「まだ推定できていない」。頭の yaw（ARCore）を北基準の方位（0〜360°）に変える関数
- **ARCore の座標系の向き（どちらが正面で、yaw の符号はどちらか）はドキュメントに書かれていない。** `docs/device-capabilities.md` の T4 の記録（+X が右、+Y が上、−Z が正面）を初期値にするが、軸と符号の取り方は定数1か所にまとめ、受け入れでの実測で直せるようにする
- 単体テスト（合成データ。実在の位置は使わない）
  - 既知のオフセット（例: 37°）で合成した歩行で、オフセットを ±2° 以内で求められる
  - 歩きながら頭を左右に振っても（頭の yaw だけ変える）、推定が変わらない
  - 曲がっている区間、遅い区間、精度が悪い区間は標本にしない
  - 外れ値の標本が混ざっても推定がぶれない
  - 時間がたつと不確かさが増える。追跡が途切れたら推定を捨てる
  - 0°/360° の境目をまたぐ値を正しく扱う

## 2. ARCore の姿勢を流すもの

- 今は `HudScene.kt` の中で `ArDevice` の姿勢を読んでいる（頭の角速度のログ用）。それとは別に、アプリ全体で使える「頭の姿勢の流れ」（位置と yaw と追跡の状態、10 Hz 程度）を用意し、`HeadingEstimator` に渡す
- `HudScene.kt` の既存の処理は変えない（T14 が同じファイルを触るおそれがあるため）。新しいクラスとして作り、`AppContainer` などから組み立てる
- XR でない端末（スマホ）や、追跡を設定できないときは、何も流さない

## 3. フィールドログに列を足す

- `FieldLogWriter` の CSV に次の列を足す（1 秒に 1 行のまま）
  - `ar_tracking`、`ar_x_m`、`ar_z_m`、`ar_yaw_deg`（区間末の ARCore の頭の姿勢）
  - `gps_bearing_deg`、`gps_bearing_acc_deg`、`gps_speed_mps`（区間内の最後の測位）
  - `north_offset_deg`、`north_uncertainty_deg`（`HeadingEstimator` の推定。無ければ空欄）
- **緯度経度と住所は今までどおり記録しない。** ARCore の位置は起動時を原点とする相対の値（m）で、地図上の位置ではない
- `docs/field-test.md` の列の表を更新する
- 既存のフィールドログのテストを更新し、新しい列のテストを足す

## 4. 分析スクリプト（`scripts/heading-analysis.py`）

- Python 3 の標準ライブラリだけで書く（この PC には Python 3.12 がある）
- フィールドログの CSV を読み、窓ごとのオフセットの標本を作って、次を出す: 標本の数、オフセットの中央値、円周標準偏差、時間あたりの変化（ドリフト、度/分）
- **軸と yaw の符号の取り方の候補（例: −Z 正面と +Z 正面、時計回りと反時計回り）ごとに同じ計算をして、どれがいちばん安定するか（標準偏差が小さいか）を示す。** 受け入れで、ARCore の座標系の向きを実測で決めるため
- `--self-test` で、既知のオフセットと既知の座標系で合成したデータを作り、正しい候補と正しいオフセットが出ることを確かめる。このタスクの中で実行して通す

## 5. 自己診断（デバッグビルド、`--es mode` で起動）

既存の `probe` / `map` / `maplite` と同じ仕組みで、次のモードを足す。結果は `AuraProbe` のログに `PASS` / `FAIL` / `SKIP` と数値で出す。

- `heading`
  - センサーの一覧（種類と名前）。方位センサー（地磁気、回転ベクトル）があるかを `PASS`/`FAIL` で出す
  - Geospatial: ARCore for Jetpack XR（`gradle/libs.versions.toml` のバージョン）に Geospatial の API があるかをライブラリで確かめ、あれば有効にする設定を試して結果を出す。API キーや Google Cloud の設定が要る場合は、**キーを追加せず**、必要なことを最終報告に書く
  - 頭の yaw の安定性: 60 秒間、追跡の状態と yaw の変化（最大と最小の差）を出す（受け入れで、グラスをかけて静止して測る）
- `speech`
  - `SpeechRecognizer.isRecognitionAvailable`、`isOnDeviceRecognitionAvailable`、認識サービスのパッケージ一覧
  - 端末内の認識で日本語（`ja-JP`）に対応しているか（`checkRecognitionSupport`）
  - `RECORD_AUDIO` の権限を求め、8 秒間、日本語で認識を試す。途中結果と最終結果が来たか、最終結果の文字列を出す（受け入れでユーザーが「東京駅」と話す）
  - `Geocoder.getFromLocationName("東京駅", 3)` の結果の件数（座標はログに出さない）
- マニフェストに `RECORD_AUDIO` を足す（既存の権限の行の後ろに追加する）
