# T29: 北の向きを「頭の向きと GPS の進行方向」から推定する（2026-11-24 屋外の試用の分析）

まず [README.md](README.md) の共通ルールを読むこと。T1〜T28 は main に入っている。分析の結果は [device-capabilities.md](../device-capabilities.md) の「屋外の歩行（ユーザーの試用、2026-11-24）」。

## 背景

屋外で8分・約730m 歩いたフィールドログで、ARCore の頭の位置は ±10cm から動かなかった（AURA は回転と首の動き程度しか渡していない）。T15 の `HeadingEstimator` は「ARCore の位置の移動の向き」と GPS の進行方向を突き合わせるので、標本が1つもできず、北の向きが最後まで推定されなかった。そのため、空の方位帯・頭を基準にした矢印・空間の印が出なかった。

同じログで、「GPS の進行方向 − 頭の yaw の向き」を外れ値（30° 超）を除いて平均すると、346/394 件で平均 154.6°、ばらつき 10° にまとまり、1分ごとの平均（140〜168°）にドリフトは見られなかった。yaw の符号は今の `HeadingAxes.YAW_TO_CLOCKWISE = -1` と合っていた。

## 決定事項

`HeadingEstimator` を、**頭の yaw と GPS の進行方向**から北のずれを推定する方式に作り替える。ARCore の位置は使わない。

- 標本（1 秒に 1 つまで）: 歩行中で、GPS の速度 ≥ 1.0 m/s、GPS の進行方向の精度 ≤ 30°（精度が無いときは直近 3 秒の進行方向のばらつき ≤ 15°）、追跡が TRACKING。標本の値は `GPS の進行方向 − 頭の向き（今の HeadingAxes の取り方で北に変換する前の値）` で、今の `bearingForYaw` と同じ符号の取り方にそろえる
- 推定: 直近 120 標本（約 2 分）の円周平均を求め、そこから 30° を超えて離れた標本を外して平均し直す（外れ値はよそ見）。標本が 20 個未満なら推定しない
- 不確かさ: 外したあとのばらつき ÷ √(標本数 ÷ 5)（隣り合う標本が似ているため 5 で割る）。下限は 8°（1分ごとの平均が ±13° ほど揺れたため）。最後の標本からの経過時間に応じて 1 分あたり 1° 増やす
- 追跡が途切れたら、今までどおり推定を捨てる
- `north_offset_deg` と `north_uncertainty_deg` は今までどおりフィールドログに出す
- `scripts/heading-analysis.py` も同じ方式に合わせる（ARCore の位置を使わない）。`--self-test` を合わせて直し、上の分析のログの形（頭の向きが歩く向きのまわりでばらつき、ときどきよそ見をする）の合成データで、既知のずれを ±5° 以内で求められることを確かめる
- 空間の印（T23）の位置の計算は、ARCore の位置がほとんど動かなくても、GPS の更新で置き直されることを確かめる（今の作りで動くはず。動かない箇所があれば直す）
- VPS（T25）はそのまま。VPS が使えるときは VPS の北を使う
