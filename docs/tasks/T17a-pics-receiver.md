## 目的

高度化PICS の信号機が出している BLE アドバタイズを、**接続せずに受信だけ**して、交差点ごとの信号の状態をアプリの中で扱えるようにする。表示（HUD）は T17b で作る。このタスクでは受信・解析・状態の管理・表示してよいかの判定・デバッグ用の再生まで。

## 絶対に守ること（PLAN.md §2.5）

- **受信だけ。** `connectGatt`、アドバタイズの送信（`BluetoothLeAdvertiser`、`startAdvertising`）、押しボタン・青延長・音響の要求は、アプリのコードに一切書かない
- 上のことを守っているかを確かめる単体テストを置く（`app/src/main` のソースに `connectGatt`、`BluetoothLeAdvertiser`、`startAdvertising` が出てこないことを確かめる）
- テスト用の Company ID `0xFFFF` を受け付けるのは**デバッグビルドだけ**。リリースビルドは `0x01CE` だけ
- 実在の交差点の ID や座標をリポジトリに置かない。テストのパケットは合成する

## 電文の形式（有志の解析による。公式の仕様ではない）

Manufacturer Specific Data の Company ID は `0x01CE`。以下のオフセットは Company ID の**後ろ**から数える。

| オフセット | 内容 |
|---|---|
| [0] | バージョン / 予約 |
| [1] | フラグ |
| [2] | メッセージの種類（0 = 識別子、1 = 位置、2 = 信号の状態） |
| [3] | メッセージ ID |
| [4..5] | 予約 |
| [6..9] | 交差点 ID（4 バイト、big-endian。16 進の文字列として扱う） |
| [10..] | 種類ごとの中身 |

- 種類 1（位置）: [10..13] が緯度、[14..17] が経度。符号付き 32 ビット、big-endian で、1,000,000 で割ると度になる。最小の長さは 18 バイト
- 種類 2（信号の状態）: [10 + i] の 1 バイトが i 番目の灯器の状態。最小の長さは 11 バイト。灯器は最大 16
  - 下位 4 ビット: 0 = 信号なし、1 = 赤、2 = 青の点滅、3 = 青、4 = 制御の外。それ以外は「不明」
  - 上位 4 ビット: 0〜7 なら残り値は「値 + 1」。8 以上は残り値が不明。**残り値の単位（秒かどうか）は確定していない**ので、単位を付けずに数として持つ
- 種類 0（識別子）: [10..] に文字列が入る。解析によって UTF-8 の名前とも ASCII の ID とも言われている。UTF-8 として読み、末尾の 0 を除いた文字列として持つ（表示に使うかは T17b で決める）
- 灯器の番号と横断の方向の対応は電文から分からない
- 長さが足りない、種類が不明などの電文は捨てる（例外を投げない）

形式はこの表をもとに実装する。GitHub の非公式の実装のコードはコピーしない。

## 作るもの

1. **解析（純粋な Kotlin）:** Manufacturer Specific Data のバイト列 → 電文のモデル。新しいパッケージ（例: `pics/`）に置く
2. **交差点ごとの状態の管理（純粋な Kotlin）:** 交差点 ID ごとに、最後の位置、灯器ごとの最後の状態、受信時刻、RSSI を持つ。時計は注入する
   - 鮮度: 最後の信号の状態の受信から 1.5 秒未満は「新しい」、1.5〜3 秒は「古い」（T17b で灰色にする）、3 秒を超えたら信号の状態を表示しない。位置は 60 秒覚えておく
3. **表示してよいかの判定（純粋な Kotlin）:** 次の条件をすべて満たす交差点のうち、いちばん近いものを1つ返す
   - 移動状態が停止中（`MotionState.STOPPED`）。高速移動中は絶対に返さない
   - 交差点の位置が分かっていて、今の位置から 30m 以内（位置が分からない交差点は返さない）
   - 信号の状態が 3 秒以内に届いている
   - 返す内容: 交差点 ID、灯器ごとの状態と残り値、鮮度（新しい / 古い）、今の位置から交差点への方位（北 0°、時計回り）と距離。方位は空の方位帯（T19b）で使う
4. **BLE スキャン（Android）:** `BluetoothLeScanner` で、Company ID のフィルタを付けてスキャンする
   - 権限 `BLUETOOTH_SCAN` を実行時に求める。`neverForLocation` は付けない（電文から位置を得るため）。マニフェストに `<uses-feature android:name="android.hardware.bluetooth_le" android:required="false" />` を足す
   - アプリが前面にあるあいだだけスキャンする。停止中は `SCAN_MODE_LOW_LATENCY`、それ以外は `SCAN_MODE_BALANCED`（電池のため）
   - Bluetooth がオフ、権限がない、BLE がない端末では、機能を静かに止める（ログだけ出す。HUD には何も出さない）
   - 状態を `StateFlow` で流し、`AppContainer` で組み立てる。HUD にはまだつながない（T17b でつなぐ）
5. **デバッグ用の再生:** 既存の `REPLAY` と同じように、ブロードキャスト（例: `io.github.yamichi77.aurawalkinfo.PICS_REPLAY`）で合成の電文を状態の管理に流せるようにする。デバッグビルドだけ
   - シナリオの例: `red_to_green`（赤で残り値が減り、青の点滅を経て青になる）、`stale`（途中で受信が途切れる）、`far`（交差点が 40m 先）、`stop`（再生をやめる）
   - 交差点の位置は、今の位置から北へ 10m などの相対で作る。交差点 ID は `DEADBEEF` などの合成値
6. **自己診断 `ble`（デバッグビルド、`--es mode ble`）:** フィルタなしで 20 秒スキャンし、受信した件数、端末の数（アドレスは出さない。数だけ）、RSSI の最小・中央値・最大、Company ID `0x01CE` と `0xFFFF` の件数と種類ごとの件数を `AuraProbe` に出す。**MAC アドレス、端末名、電文の中身（座標を含む）はログに出さない**
7. **テスト用の送信の手順（任意）:** 受け入れで、実物がない場所で受信を確かめるための手順を `docs/device-capabilities.md` に書く。スマホのアプリ（nRF Connect など）で Company ID `0xFFFF` の合成の電文を送る手順にする。PC から送るスクリプトを作る場合も、Company ID は `0xFFFF` に固定し、屋内だけで使うと明記する
8. `scripts/device-check.sh` に `--only ble,pics` で動くチェック（`ble` の自己診断と、`PICS_REPLAY` で状態が変わることのログ確認）を足す。今は実機で動かせないので `bash -n` で文法だけ確かめる

## 確認手順

1. `./gradlew test assembleDebug` が通る（JDK 21）
2. 単体テスト
   - 解析: 種類 0/1/2 の正しい電文、長さが足りない電文、不明な種類、不明な状態の値、残り値の 0〜7 と 8 以上、16 灯器、緯度経度の負の値
   - Company ID: リリースの設定では `0xFFFF` を捨て、デバッグの設定では受け付ける
   - 鮮度: 1.5 秒と 3 秒の境目、位置の 60 秒

   - 受信だけであることを確かめるテスト（上の「絶対に守ること」）
3. `bash -n scripts/device-check.sh` が通る
4. 既存のテストがすべて通る
5. **実機（adb）は使わない（インストールもしない）**
